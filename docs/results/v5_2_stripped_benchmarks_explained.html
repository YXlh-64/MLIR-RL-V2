What "Stripped" Means in MLIR-RL Full-Model Benchmarks

Clarifying the weight-stripping pipeline, mathematical validity, and implementation details for V5.2 full-model evaluation

The 30-Second Summary

In v5_2_full_model_support.html, "stripped" refers specifically to weight-stripping: eliminating the massive text-encoded floating-point constants (neural network weights) from the .mlir files and replacing them with zero splats (dense<0.0>).

The neural network structure (all layers, tensor shapes, loop nests, operators, and data-flow dependencies) remains 100% intact. Only the numerical values inside the constants were discarded to save 14.5 GB of text bloat and prevent parser / bufferization crashes.

1. The Problem: The Text-Encoded Weight Bloat Crisis

When high-level deep learning models (PyTorch / ONNX) are exported and lowered through torch-mlir to the linalg dialect, model parameter weights (e.g. convolution kernels, projection matrices, embeddings) are embedded directly into the human-readable .mlir text files.

For large neural networks, this produced an extreme volume of ASCII text:

  • LLaMA 3.2 1B: Generated a single 9.43 GB text file.
  • GPT-2: Generated a 2.71 GB text file.
  • BERT: Generated an 835.6 MB text file.
  • ViT-B/16: Generated a 660.7 MB text file.
  • BART: Generated a 625.1 MB text file.

Why Weight Bloat Broke the System

  1. Parser & AST Dumper Out-Of-Memory (OOM): Python string processing and LLVM lexers had to allocate and scan tens of gigabytes of text in memory. Probing LLaMA 3.2 1B immediately killed the worker process.
  2. Bufferization Failures: MLIR's one_shot_bufferize pass crashed with "op was not bufferized" or memory allocation exhaustion when trying to allocate buffers for millions of raw text-defined float constants.
  3. Slurm Job Aborts: Workers running multiple jobs hit node memory limits (e.g. 32 GB Slurm allocations were killed by sacct OUT_OF_MEMORY).

2. The Core Principle: Why Weight Values Do Not Matter for RL Scheduling

In typical model inference, weights cannot be altered because they determine prediction accuracy. However, in MLIR-RL:

The Latency Invariance Principle

Loop transformations and execution latency depend entirely on loop bounds, array dimensions, memory access strides, and operator types — not on the specific floating-point values inside memory.

  • Multiplying a 768x3072 matrix by 0.74129 takes the exact same number of clock cycles, SIMD vector instructions, cache line traversals, and memory memory writes as multiplying by 0.0.
  • MLIR-RL evaluates execution speedup: speedup = baseline_exec_time / optimized_exec_time measured via an in-memory @nanoTime() delta.
  • The RL evaluation pipeline never inspects or verifies the numeric tensor outputs. It only measures the runtime nanoseconds of the compiled binary.

3. What Happened: Step-by-Step Breakdown

1 Identifying Weight Representations in Raw MLIR

In the original unstripped files, weights appeared in three problematic forms:

  1. Hex-encoded constant strings: e.g., dense<"0x775AB7BC85D52F3C..."> : tensor<3072x768xf32>, spanning millions of characters per line.
  2. Long numeric float arrays: e.g., dense<[1.042, -0.231, ... ]> containing thousands of formatted ASCII numbers.
  3. Torch tensor dialect resources: e.g., dense_resource<torch_tensor_42_torch.float32> pointing to a multi-gigabyte binary payload delimited by {-# dialect_resources: { ... } #-} at the end of the file.
2 Offline Stripping with data_utils/postprocess/strip_mlir.py

The stripping tool processes these massive files to produce compact, well-formed MLIR files:

  • Streaming Line-by-Line Processing: For files >100 MB, the script avoids reading the entire file into RAM, streaming line-by-line so it can strip a 9.4 GB file with only ~10 MB of memory usage.
  • Regex Constant Replacement: Matches all hex and numeric constant arrays and replaces them with dense_resource<__elided__>.
  • Payload Truncation: Truncates the file immediately before {-# dialect_resources, discarding the multi-gigabyte binary trailer.
  • Result: Saves stripped versions into data/full_models/relowered/.
3 In-Memory Materialization with rl_autoschedular_v5/full_model.py

MLIR's JIT compiler cannot execute a file containing dense_resource<__elided__> directly because the resource entry does not exist on disk. When Benchmarks loads the code into memory, materialize_elided_resources() intercepts it:

# rl_autoschedular_v5/full_model.py
def _elided_repl(match: re.Match) -> str:
    shape = match.group(1)
    etype = shape.split('x')[-1]
    # Use dense<0> for integers, booleans, and indices; dense<0.0> for floats
    zero = '0' if (etype.startswith('i') or etype == 'index') else '0.0'
    return f'dense<{zero}> : tensor<{shape}>'

def materialize_elided_resources(code: str) -> str:
    if '__elided__' not in code:
        return code
    return _ELIDED_RE.sub(_elided_repl, code)

This replaces the placeholder with an element-type-safe zero splat (e.g. dense<0.0> : tensor<3072x768xf32>). A zero splat requires only a few bytes in the MLIR AST and bufferizes instantly without memory bloat.

4 TIMED ABI Wrapping & Baseline Recalibration

Once weights are materialized as zero splats:

  1. ensure_timed_main_abi() wraps the model entry in @nanoTime() timing probes and standardizes the function signature to @main(...) -> (tensors..., i64).
  2. Baselines were re-measured on these exact stripped artifacts via scripts/baseline/baseline_fullmodels.py to ensure that baseline and optimized runs are evaluated under identical conditions.
